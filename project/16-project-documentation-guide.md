# How to Document Each Project in PMA

## Overview

Every project in PMA is a single Markdown file under `<md_root>/<OU>/Projects/<project-name>.md`. The file is the authoritative record for everything about that project. PMA's AI, materialiser, indexer, and news watch all read from this file. What you put in it directly determines how well PMA can assist you.

## Project File Location

```
<md_root>/
  <OU-Name>/
    Projects/
      <project-name>.md     # one file per project
      Index.md              # AUTO-GENERATED — do not edit
```

- **OU-Name**: Organisational unit (e.g. `Infrastructure`, `Marketing`, `PersonalProjects`)
- **project-name**: Short kebab-case or PascalCase filename (e.g. `cloud-migration.md`, `Q3-Campaign.md`)
- **Index.md**: Auto-regenerated by materialiser every nightly run — summarises all projects in the OU. Do not edit.

## Complete Project File Template

```markdown
---
key: PROJ-KEY             # Short unique identifier (e.g. IT-DOM25, MKT-Q3CAM)
title: Full Project Title
status: active            # active | paused | complete | archived
priority: P1              # P1 | P2 | P3
owner: "@KLA"             # @nick from People.md
```

## Section-by-Section Guide

### YAML Frontmatter

The frontmatter is parsed by the materialiser, news watch, and housekeeping. Get it right.

```yaml
---
key: IT-DOM25
title: Domain Migration 2025
status: active
priority: P2
owner: "@KLA"
flag: important
news_topics:
  - DNS migration enterprise
  - Active Directory domain join
---
```

#### `key:` (Required)
- Short stable identifier: `OU-ABBREV-TOPIC` pattern (e.g. `IT-DOM25`, `MKT-Q3`)
- Used by plan pipe to prefix tasks: `- [ ] IT-DOM25: Task name due:Jun-15`
- Used by news watch as the project identifier in batch requests
- Must be alphanumeric + hyphens only (for Anthropic custom_id compatibility)
- Once set, do not change (existing ^R markers and plan references use it)

#### `title:` (Required)
- Full human-readable title
- Shown in project index, plan files, and govern tracking

#### `status:` (Required)
Possible values:
| Value | Meaning | News Watch | Materialiser |
|-------|---------|-----------|-------------|
| `active` | In progress | ✅ Included | ✅ Included |
| `paused` | On hold | ❌ Skipped | ❌ Skipped |
| `complete` | Done | ❌ Skipped | ❌ Skipped |
| `archived` | Historical reference | ❌ Skipped | ❌ Skipped |

Only `active` projects are processed by news watch and the materialiser. When a project is done, set `status: complete`.

#### `priority:` (Optional)
| Value | Meaning |
|-------|---------|
| `P1` | Critical — must do this week. Carry-forward gets priority sorting. |
| `P2` | Important — should do this month |
| `P3` | Nice to have — do when bandwidth allows |

#### `owner:` (Optional)
- `@nick` from People.md
- Sets the default owner for tasks generated from this project's Playbook
- For team projects: set to the DRI (directly responsible individual)

#### `flag:` (Optional)
Affects news watch item budget:
| Value | Items/Topic |
|-------|-------------|
| `star` | 5 |
| `important` | 5 |
| `urgent` | 5 |
| *(absent)* | 2 (or 5 if recently edited) |

#### `news_topics:` (Optional)
List of search queries for news watch. Tips:
- Be specific: "kubernetes security vulnerabilities" > "kubernetes"
- Combine product + concern: "AWS Lambda cold start performance"
- Include company/product names: "Anthropic Claude API updates"
- Add regulatory context: "GDPR data residency Europe"
- Omit for internal projects with no external news relevance (saves batch credits)

### `## Purpose` Section

The AI reads this section as `purpose_context` for every chat session scoped to this OU. Write it to give the AI the background it needs to help you:

**Good:**
```markdown
## Purpose
Migrate our 200-person company from legacy on-premise Active Directory to 
Entra ID (Azure AD) to enable zero-trust security posture and support our 
remote-first workforce. The migration has a hard deadline of Q3 2026 due to 
the on-premise contract expiry. Current blocker: legacy LOB apps not yet 
AAD-compatible.
```

**Too sparse:**
```markdown
## Purpose
Domain migration project.
```

The purpose is included verbatim in every AI chat system prompt for this OU. It should answer:
- What is being built/changed?
- Why does it matter?
- Who is it for?
- What are the constraints or blockers?

### `## Goals` Section

Concrete, measurable goals. The AI uses these for task suggestion and progress reviews:

```markdown
## Goals
- Migrate all 200 user accounts to Entra ID by 2026-09-01
- Decommission on-premise domain controllers by 2026-10-01
- All LOB apps pass AAD auth test by 2026-08-15
- Achieve 99.9% MFA enrollment rate before cutover
```

### `## Tasks` Section

This is where work happens. Key rules:

#### Task States
```markdown
- [ ] Pending — needs to be done
- [x] Done — completed
- [>] Scheduled — activated by plan pipe (do NOT set manually)
- [-] Cancelled — won't do
```

#### Task Annotations
```
- [ ] Deploy staging environment start:2026-07-01
- [ ] Complete UAT due:2026-08-15
- [ ] Write runbook @KLA due:Jun-30
- [ ] Create Jira epic JIRA:IT-89
- [ ] Migrate pilot group of 20 users P1 due:2026-07-15
```

| Annotation | Format | Meaning |
|-----------|--------|---------|
| `start:` | `start:YYYY-MM-DD` or `start:Mmm-DD` | Plan pipe activates this task on start date |
| `due:` | `due:YYYY-MM-DD` or `due:Mmm-DD` | Plan pipe activates this task on due date |
| `@nick` | `@KLA`, `@JD` | Assigned to person (nick from People.md) |
| `JIRA:KEY` | `JIRA:IT-89` | Linked Jira issue — synced by jira_sync_job |
| `P1/P2/P3` | `P1` | Priority override for this task |

#### Do Not Edit `[>]` Tasks
Tasks marked `[>]` were moved there by the materialiser's plan pipe (they have a `start:` or `due:` date that matched today). Editing them confuses the idempotency system. Instead:
- To complete: change `[>]` → `[x]`
- To cancel: change `[>]` → `[-]`
- To reschedule: add a new `- [ ]` task with the new date; leave the `[>]` for today's daily log

### `## Recurring` Section

**Do not write in this section manually.** The materialiser writes here when Playbook tasks are materialised. Content looks like:

```markdown
## Recurring

- [ ] Monthly status report @KLA due:Jun-30 SMTW/Recur/status-report.md ^P:status-report-M06
- [ ] Quarterly OKR review due:2026-06-30 SMTW/Recur/okr-review.md ^P:okr-review-Q2
```

### `## Playbook` Section (Optional)

Define project-specific recurring tasks here. Unlike `<OU>/Recur/` files (which route to Daily), Playbook instances appear only in this project's own `## Recurring` section:

```markdown
## Playbook

- title: Monthly status report
  cadence: monthly
  schedule: day:last-week
  owner: "@KLA"
  priority: P2

- title: Quarterly steering committee deck
  cadence: quarterly
  schedule: m3-day:last-week
  owner: "@KLA"
  priority: P1
  body: |
    Prepare slides covering: progress vs. goals, blockers, budget status,
    next quarter milestones. Send to @CEO 3 days before the meeting.
```

Cadence + schedule options (same as Recur files):
- `cadence: monthly` + `schedule: day:15` — 15th of each month
- `cadence: monthly` + `schedule: day:last` — last day of month
- `cadence: quarterly` + `schedule: m1-15` — 15th of first month of each quarter
- `cadence: yearly` + `schedule: day:04-15` — April 15th every year

### `## Notes` Section

The most underused but highest-value section. The AI uses this section for RAG context. Use it for:

```markdown
## Notes

### Architecture Decisions
- Chose hybrid sync (ADConnect) for phase 1 to allow rollback
- LOB apps using NTLM must be migrated before full cutover
- Pilot group: IT team (8 people) + Volunteers (12 people) = 20 total

### Risks
- Vendor X app does not support SAML — needs custom proxy
- Legal requires audit log of all auth events during cutover period

### Meeting Notes: 2026-06-10 Steering Committee
- Budget approved: $45,000 for migration tooling
- Exec sponsor: CTO
- Timeline accepted

### Open Questions
- Does LOB App Y support Entra ID conditional access?
- What's the process for emergency break-glass accounts?
```

Tip: The more context you put in `## Notes`, the better the AI performs for this project. ChromaDB indexes this section and retrieves it when you ask project-related questions.

### `## Links` Section

Markdown links to external resources:

```markdown
## Links
- [Migration playbook](https://wiki.company.com/entra-migration): Step-by-step guide
- [Jira Epic](https://company.atlassian.net/browse/IT-89): All tickets
- [Slack #it-migration](slack://channel/...): Team discussion
- [Vendor support ticket](https://vendor.com/...): LOB app compatibility issue
```

### `## AI Notes` Section

The AI writes here when you ask it to take notes or record decisions. Do not delete this section header — the AI looks for it to append structured observations:

```markdown
## AI Notes

2026-06-18: User confirmed pilot scope is IT team + 12 volunteers. Cutover
planned for last week of August. LOB App Y still blocked on vendor response.
```

### `## Log` Section

Chronological event log. Can be append-only or newest-first — pick one style and stick to it:

```markdown
## Log

2026-06-18: Kicked off project. ADConnect lab environment set up.
2026-06-20: Pilot group identified and briefed.
2026-06-25: LOB App Y compatibility issue escalated to vendor.
```

## Section Order Requirement

The materialiser and AI both rely on sections appearing in this order. Violating the order causes materialiser to insert content in wrong locations:

1. YAML frontmatter (`---`)
2. `# Title`
3. `## Purpose`
4. `## Goals`
5. `## Tasks`
6. `## Recurring` ← materialiser writes here
7. `## Playbook` ← optional
8. `## Notes`
9. `## Links`
10. `## AI Notes` ← always second-to-last
11. `## Log` ← always last

The materialiser inserts new sections ABOVE `## AI Notes` and `## Log` to preserve their trailing position.

## Project Index Auto-Generation

Every nightly materialiser run rebuilds `<OU>/Projects/Index.md`:

```markdown
# Project Index — Infrastructure

| Key | Title | Status | Priority | Owner |
|-----|-------|--------|----------|-------|
| IT-DOM25 | Domain Migration 2025 | active | P1 | @KLA |
| IT-MON26 | Monitoring Overhaul | active | P2 | @JD |
| IT-NET24 | Network Refresh | complete | P2 | @KLA |
```

**Do not edit `Index.md`** — it is overwritten on every run. All project metadata comes from individual project file frontmatter.

## ChromaDB Indexing

Each project file is indexed into ChromaDB when:
1. The file is saved via `PUT /api/corpus/file` (immediate `refresh_single_file`)
2. The worker's `index_sync_job` detects mtime change (every 300s)
3. Manual reindex via `POST /api/corpus/reindex`

ChromaDB metadata per chunk:
```python
{
    "ou": "Infrastructure",          # from folder path
    "path": "Infrastructure/Projects/cloud-migration.md",
    "mtime": 1234567890.123,
    "archived": "false",             # string, not bool
}
```

The AI's `search_corpus` tool queries ChromaDB and retrieves relevant chunks from your project files to answer questions.

## Best Practices

### Do
- Write a detailed `## Purpose` — it's in every AI chat system prompt for this OU
- Add `due:` dates to important tasks — the plan pipe will surface them in your Daily
- Use `news_topics:` for external-facing projects (products, compliance, partnerships)
- Add `flag: important` for projects that need daily news monitoring
- Keep `## Notes` up to date — the AI retrieves this for context
- Set `status: complete` when done rather than leaving projects active forever
- Use `JIRA:KEY` on tasks that have corresponding Jira issues

### Don't
- Don't edit `[>]` tasks (managed by plan pipe)
- Don't edit `^R:` or `^P:` markers (idempotency anchors)
- Don't edit `## Recurring` (materialiser writes here)
- Don't edit `Index.md` (auto-generated)
- Don't put sensitive secrets in project files (they are git-committed)
- Don't nest subfolders inside `Projects/` — materialiser expects flat structure
- Don't use `@` in frontmatter without quoting: use `"@KLA"` not `@KLA`

## Example: Minimal vs Full Project File

### Minimal (functional but limited AI assistance)
```markdown
---
key: MISC-WEB
title: Website Redesign
status: active
---

# Website Redesign

## Purpose
Redesign the company website.

## Tasks
- [ ] Define requirements due:2026-07-01
- [ ] Select design agency due:2026-07-15
```

### Full (maximum AI assistance)
```markdown
---
key: MKT-WEB26
title: Website Redesign 2026
status: active
priority: P1
owner: "@SJ"
flag: important
news_topics:
```
